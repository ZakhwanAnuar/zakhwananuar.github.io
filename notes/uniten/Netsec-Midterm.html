Chapter 1 — Introduction

Overview of Computer Network & the Internet

  • Computer network — a group of computer systems & computing hardware linked together through communication links; facilitates communication & resource sharing among users.
  • The Internet — an interconnection of networks (a network of networks) that connects all networks in the world into one big network; also an infrastructure providing services to applications.
  • Hosts / end systems — devices connected to the Internet that run network applications.
  • End systems are connected by communication links and packet switches (switches & routers).
  • Different links transmit at different transmission rates.
  • End systems access the Internet through ISPs (Internet Service Providers).
  • Principal Internet protocols = TCP/IP.
  • IETF (Internet Engineering Task Force) develops & maintains Internet standards.
  • Internet standard documents are called RFCs (Requests for Comments).

Network Protocols

  • Define the rules used in communication (like rules of a language).
  • Enable interoperability of networking technologies.
  • A protocol defines:
    • Type of messages exchanged
    • Syntax of message types
    • Semantics of fields
    • Rules for when/how a process sends & responds to messages

Protocol Architecture

  • Communication tasks are complex → broken into modules.
  • A protocol architecture is a layered structure of these modules; each layer performs a subset of tasks.
  • Two common architectures:
    • OSI reference model
    • TCP/IP protocol stack ← the one used by the Internet

What Can the Bad Guys Do?

  • Sniff packets and steal your data.
  • Masquerade as someone you trust.
  • Attack servers and network infrastructure.
  • Install malware in your host via the Internet.

Network Security Objectives

  • Network security = measures to deter, prevent, detect, and correct security violations involving transmission of information.
  • Core objectives (CIA):
    • Confidentiality — data confidentiality + privacy
    • Integrity — data integrity + system integrity
    • Availability
  • Two additional objectives for network security:
    • Authenticity — verify users are who they say they are, and that inputs come from a trusted source.
    • Accountability (non-repudiation) — actions of an entity can be traced uniquely to that entity.

Network Security Challenges

  • Security is not simple.
  • Must consider potential attacks on the security features.
  • Procedures are often counter-intuitive.
  • Need to decide where to use security mechanisms.
  • Requires constant monitoring.
  • Is too often an afterthought.
  • Mechanisms involve more than a single algorithm/protocol.
  • Security is a battle of wits between perpetrator & designer.
  • Little perceived benefit until a security failure occurs.
  • Strong security is often viewed as an impediment to efficiency/user-friendliness.

OSI Security Architecture (ITU-T X.800)

  • Provides a systematic way to define security & characterize approaches to satisfy requirements.
  • Three components:
    • Security attack — any action that compromises the security of information.
    • Security service — a processing/communication service that enhances security; intended to counter attacks; uses one or more security mechanisms.
    • Security mechanism — a process/device designed to detect, prevent, or recover from a security attack.

Security Attacks — Passive vs Active

  • Passive attack — attempts to learn/use information but does not affect system resources.
  • Active attack — attempts to alter system resources or affect their operation.

Passive Attacks (2 types)

  • Release of message contents — attacker reads the content of the transmitted message.
  • Traffic analysis — attacker observes the pattern of messages (location, identity, frequency, length) without reading them; can guess the nature of the communication.

Active Attacks (4 types)

TypeDescription
MasqueradeOne entity pretends to be a different entity; usually includes one of the other active attacks.
ReplayPassive capture of a data unit and subsequent retransmission to produce an unauthorized effect.
Modification of messagesSome portion of a legitimate message is altered, or messages are delayed/reordered.
Denial of servicePrevents or inhibits the normal use/management of communications facilities.
Tip: Some active attacks can be prevented with mechanisms; some are hard to prevent due to wide variety of physical, software, and network vulnerabilities.

Security Services (X.800 categories)

  • X.800 definition: a service provided by a protocol layer of communicating open systems that ensures adequate security of systems/data transfers.
  • RFC 4949 definition: a processing/communication service that gives a specific kind of protection to system resources.
  • Five categories: Authentication, Access control, Data confidentiality, Data integrity, Non-repudiation.
ServicePurpose
AuthenticationAssure that communication is authentic. Two types: peer entity authentication and data origin authentication.
Access controlLimit & control access to host systems/applications via communications links; each entity must be identified/authenticated first.
Data confidentialityProtect transmitted data from passive attacks; includes protecting traffic flow from analysis.
Data integrityConnection-oriented (stream of messages, no duplication/insertion/modification/reorder/replay) or connectionless (single message, modification only).
Non-repudiationPrevents sender or receiver from denying a transmitted message.
AvailabilitySystem/resource accessible & usable on demand; addresses DoS attacks; depends on management/control of resources.

Attack Surface

  • Attack surface — set of points on the boundary of a system where an attacker can enter, cause an attack, or extract data.
  • Examples: open ports, services inside a firewall, code processing incoming data (email/XML/office documents), interfaces/SQL/Web forms, employees vulnerable to social engineering.

Attack Surface Categories

  • Network attack surface — vulnerabilities over enterprise/WAN/Internet.
  • Software attack surface — vulnerabilities in application, utility, or OS code.
  • Human attack surface — vulnerabilities from personnel/outsiders (social engineering, human error, trusted insiders).

Attack Vector & Attack Tree

  • Attack vector — a path by which a threat actor can gain access to a server/host/network; can originate from inside or outside the network.
  • Attack tree — a branching, hierarchical data structure representing a set of potential techniques for exploiting vulnerabilities.
    • Root node = the security incident (goal of the attack).
    • Branches/subnodes = ways to reach the goal.
    • Leaf nodes = different ways to initiate the attack.
    • Branches may be labeled with difficulty/cost to compare attacks.

Chapter 2 — Web & Transport-layer Security

Network Applications

  • Network application — a computer application that requires communication over the network; at least a client and a server (normally on two different hosts).
  • Application-layer protocol lets client & server communicate.
  • Most application-layer protocols were not developed with security in mind (early Internet days); security features must be added on top of existing protocols.

  • Open-standard protocols are defined in RFC documents (e.g. HTTP → RFC 2616; SMTP → RFC 821, latest RFC 5321).

The Internet's Transport Layer

  • Two transport protocols: UDP (User Datagram Protocol) and TCP (Transmission Control Protocol).
  • Applications choose one based on requirements.
  • Most Internet applications use TCP (reliable data delivery).

Port Numbers

  • A port number identifies a network application running on a host; only one application can use a given port.
  • Well-known ports: 0–1023 (defined in RFC 1700 & RFC 3232).
  • Client-side dynamic/ephemeral ports: 49152–65535.
  • A packet sent to a port is received by the app using that port → port is a "door" to the application; each open port is an attack surface → close unused ports.

Overview of TCP

  • Connection-oriented — a connection must be established before data transfer.
  • Connection establishment = three-way handshake:
    1. Client sends a special TCP segment.
    2. Server responds with a second special segment.
    3. Client responds again with a third segment (may include application-layer data).
  • Connection-first allows reliable transfer & congestion control.

TCP Segment Structure

  • Source & destination port — process-to-process delivery.
  • Checksum — error detection.
  • 32-bit sequence number & acknowledgement number — reliable data transfer.
  • 4-bit length — header length in 32-bit words (variable due to options).
  • 16-bit receive window — number of bytes receiver willing to accept (flow control).

TCP Flags (6 bits)

  • ACK — whether acknowledgement field is valid.
  • RST, SYN, FIN — connection setup & teardown.
  • PSH — receiver should pass data to upper layer immediately.
  • URG — data marked "urgent"; location of last urgent byte indicated by urgent data pointer.

Overview of HTTP

  • HTTP is a file transfer protocol initially developed for the Web.
  • Versions: HTTP/1.0 (RFC 1945), HTTP/1.1 (RFC 2616), HTTP/2, HTTP/3.
  • Also used by P2P file sharing, instant messaging, audio/video streaming.
  • Ports 80 & 443 are among the few ports open for outbound communication in most firewalls.
  • Web page = objects stored at the server (HTML, JPEG, applet, audio…). Base HTML + referenced objects.
  • URL components: protocol (http), server hostname (www.uniten.edu.my), object path name (/cci/index.html).

HTTP Request Methods

  • GET — get an object.
  • POST — submit data to server (e.g. form).
  • HEAD — get response header only (debugging).
  • PUT — upload an object to a path.
  • DELETE — delete an object.

HTTP Status Codes

HTTP Cookies

  • HTTP is stateless (doesn't store user info); cookies identify users.
  • Cookies allow a site to: restrict access, serve content by identity, maintain session, offer shopping cart.
  • Three components:
    1. Cookie header line in HTTP response.
    2. Cookie file on user's system (managed by browser).
    3. Back-end database at the Web site.

Cookie Security/Privacy Issues

  • Session hijacking — captured cookies bypass authentication & impersonate users.
  • XSS — malicious scripts access cookies if not marked HttpOnly.
  • CSRF — trick users into submitting requests using their cookies.
  • Third-party cookies — track users across sites → loss of privacy.
  • Cookie overflow — exploit storage limit → DoS or overwrite cookies.

Web Proxy

  • A network entity that satisfies HTTP requests on behalf of a client.
  • Benefits: caching (faster response), reduce traffic, control/monitor access.
  • Anonymous proxies make activity untraceable & bypass controls; third-party proxies may be malicious.

TLS (Transport Layer Security)

  • Evolved from SSL (Secure Sockets Layer). Latest version TLS 1.3 (RFC 8446, Aug 2018). TLS 1.2 & 1.3 commonly used.
  • General-purpose service implemented as a set of protocols relying on TCP.
  • Two implementation choices:
    • Implement TLS in specific applications (most common, e.g. Web browsers).
    • Implement TLS as part of the underlying protocol suite (e.g. QUIC/HTTP-3).
  • Security services provided: data encryption, data integrity, server (optionally client) authentication via digital certificate.

TLS Session vs Connection

  • TLS session — association between client & server; created by Handshake Protocol; defines shared cryptographic parameters.
  • TLS connection — a live communication channel for data transfer; managed by Record Protocol; a session can have multiple connections.

Session state parameters: session identifier, peer certificate (X.509v3, may be null), compression method, cipher spec, master secret (48-byte), is-resumable flag.

Connection state parameters: server/client random, server write MAC secret, client write MAC secret, server write key, client write key, sequence numbers (64-bit counters; prevent replay & ensure ordering).

TLS Record Protocol

  • Provides confidentiality (shared secret key for encryption) and message integrity (shared key for MAC).
  • Operations on application data: Fragmentation → Compression → Add MAC → Encrypt.
  • Fragmentation — into blocks of 2¹⁴ (16,384) bytes or less.
  • Compression — optional; removed in TLS 1.3.
  • Encryption (TLS 1.3) — only AEAD (Authenticated Encryption with Additional Data):
    • Block cipher: AES GCM or AES CCM
    • Stream cipher: ChaCha20-Poly1305
    • AEAD does encryption + authentication (no separate MAC).

Record header fields: Content type (8 bits: change_cipher_spec, alert, handshake, application_data), Protocol version (16 bits: TLS 1.2 = 0x0303), Compressed length (16 bits).

Other TLS Protocols

  • Change Cipher Spec Protocol — tells receiver subsequent records use the just-negotiated cipher spec & keys; single byte value 1.
  • Alert Protocol — conveys TLS alerts; two bytes: level (1=warning, 2=fatal) + alert code. Fatal → terminate.
  • Handshake Protocol — authenticates server/client & negotiates: encryption algorithm, cryptographic keys, MAC algorithm. Message fields: Type (1 byte), Length (3 bytes), Content (≥0 bytes). Must happen before application data.
TLS 1.3 reduces the number of handshake messages exchanged (performance).

HTTPS (HTTP over TLS)

  • Combination of HTTP + TLS for secure browser–server communication.
  • Uses port 443; URL begins with https://; documented in RFC 2818.
  • Security services:
    • End-to-end confidentiality — all HTTP traffic encrypted.
    • Message integrity — MAC (TLS 1.2) or AEAD (TLS 1.3).
    • Server authentication — digital certificate issued by CA (self-signed → browser warning).
  • Encrypted elements: URL, document contents, browser form contents, cookies, HTTP header contents.
  • TLS handshake happens before the first HTTP request; all HTTP data sent as TLS application data.

SSL/TLS Attacks

Four categories:

  • Handshake protocol attacks — downgrade, MITM, invalid curve.
  • Record/application data attacks — BEAST, POODLE, Lucky13, replay.
  • PKI attacks — rogue CA, certificate spoofing, weak key generation.
  • Other — implementation flaws, side-channel, CRIME/BREACH.
AttackDetailMitigation
POODLETLS ≤1.2 with CBC; modifies padding bytes to decipher a block.Avoid CBC, use AEAD (TLS 1.3 removed CBC).
BEASTTLS ≤1.2 with CBC; exploits predictable IV.Avoid CBC, use AEAD.

SSH (Secure Shell)

  • Protocol for secure network communication; current version SSH2 (RFC 4250–4256).
  • Originally a secure remote-login replacement for telnet; now general client/server capability (SFTP, SCP, SSHFS, passwordless login, port forwarding, VPN, X11 forwarding).

SSH Transport Layer Protocol

  • Server authentication at transport layer via public/private key pair (host key).
  • Two trust models (RFC 4251):
    1. Client has a local database mapping host name → public host key.
    2. Host name→key certified by a trusted CA; client knows CA root key.

SSH Authentication Methods

  • Password — protected by Transport Layer encryption.
  • Publickey — private key on client, public key on server; server sends challenge encrypted with client's public key.
  • Hostbased — key for a host; authenticates all users on the client host.

SSH Connection Protocol

  • Runs on top of Transport Layer; uses a secure authenticated connection (a tunnel) to multiplex logical channels.
  • Four channel types: session (remote program execution), x11 (GUI), forwarded-tcpip (remote port forwarding), direct-tcpip (local port forwarding).

Port Forwarding

  • Converts insecure TCP connections into secure SSH connections (SSH tunneling).
  • Local forwarding — creates a port on local machine to access internal service securely.
  • Remote forwarding — creates a port on remote SSH server to share a local service.

Chapter 3 — Email & DNS Security

Email Architecture (RFC 5598)

  • Administrative Management Domain (ADMD) — the Internet email provider that manages the MTA (Mail Transfer Agent); each has different operating policies & trust-based decisions.
  • DNS — directory lookup mapping hostname ↔ IP address (e.g. finds the email server for uniten.edu.my).

Email Protocols

  • SMTP (Simple Mail Transfer Protocol) — sends email between hosts. Originally RFC 821 (1982, text-only), current RFC 5321 (Oct 2008).
  • ESMTP (Extended SMTP, RFC 1869) — better security, attachments, multiple recipients.
  • Mail access protocols for retrieval: POP3, IMAP, Exchange.
SMTP transcript example — commands: HELO, MAIL FROM, RCPT TO, DATA (ends with "." on a line by itself), QUIT.

Mail Access Protocols

ProtocolPortNotes
POP3110RFC 1939; downloads email; username/password.
IMAP143RFC 2060; more complex; folders on server; retrieve message components; stronger auth.
HTTP (Webmail)—Web browser access; IMAP used at the back.

Mail Message Format (RFC 5322)

  • Headers include: Subject, From, To, Date.
  • Headers are placed before the body; entered after SMTP "DATA".
  • Header lines and body separated by a blank line.

MIME Extension

  • SMTP requires 7-bit ASCII body → hard to send non-ASCII data.
  • MIME (Multipurpose Internet Mail Extension, RFC 2045/2046) adds headers & content formats for multimedia.
  • Five MIME header fields:
    • MIME-Version — conforms to RFC 2045/2046.
    • Content-Type — describes body data.
    • Content-Transfer-Encoding — transformation used for transport.
    • Content-ID — unique identification of MIME entities.
    • Content-Description — text description of the object.

Email Threats & Mitigations

Threat classification:

  • Authenticity — unauthorized access / masquerading as trusted sender.
  • Integrity — unauthorized modification of content.
  • Confidentiality — unauthorized disclosure.
  • Availability — prevent sending/receiving.

S/MIME

  • Security enhancement to MIME; defined in multiple RFCs (5750, 5751, 4134, 2634, 5652, 3370, 5752, 1847).

Services

  • Authentication — digital signature (RSA + SHA-256). Sender: hash → encrypt digest with private key. Receiver: decrypt with public key, recompute hash, compare.
  • Confidentiality — encryption (AES-128, CBC mode). Content-encryption key (random 128-bit, used once) encrypts message; the key itself is encrypted with recipient's public key (RSA).
  • Email compatibility — 7-bit encoding (Base64: 3 octets → 4 ASCII chars).
  • Compression — saves space; RFC 5751 guidelines: compressing binary-encoded encrypted data discouraged; if lossy + signing, compress first then sign.

Message Content Types (RFC 5652)

  • Data — inner MIME-encoded content.
  • SignedData — apply digital signature.
  • EnvelopedData — encrypted content + encrypted content-encryption keys.
  • CompressedData — apply compression.

Certificate Processing

  • Uses X.509 v3 certificates signed by CA.
  • Management: key generation, registration (with CA), certificate storage & retrieval.

Enhanced Security Services (RFC 2634)

  • Signed receipts — proof of delivery.
  • Security labels — sensitivity info; access control.
  • Secure mailing lists — recipient-specific encryption.
  • Signing certificates — bind sender's certificate to signature.

PGP / OpenPGP

  • Alternative email security, same functionality as S/MIME. Created by Phil Zimmerman, first released 1991.
  • OpenPGP — standard based on PGP 5.x; RFC 4880 & RFC 3156.

S/MIME vs OpenPGP

AspectS/MIMEOpenPGP
Key certificationX.509 certs from CAUsers generate own keys; signed by trusted keys (Web-of-Trust)

SP 800-177 recommends S/MIME over PGP due to greater confidence in the CA system.

Domain Name System (DNS)

  • Directory lookup service mapping hostname ↔ IP address; essential to Internet.
  • No single server has all mappings; distributed.
  • Three classes of servers: Root, TLD, Authoritative.
  • 13 root DNS servers (a.root-servers.net – m.root-servers.net), each a server cluster.
  • TLD servers: com, org, net, edu + country TLDs (my, sg, uk…).
  • Authoritative servers hold mappings of an organization's public hosts.

DNS Security Issues

  • DNS spoofing / cache poisoning — attacker intercepts query, replies with own answer (maps to attacker's IP).
  • DNS server attack — exploit software bugs; DoS (DNS Amplification Attack).

DNSSEC

  • Protects DNS clients from forged/altered resource records via digital signatures by zone administrators, verified by resolver.
  • New RR types + protocol modifications. RFC 4033, 4034, 4035.
  • DNSSEC only authenticates, does not encrypt. Implemented only between DNS servers.

DANE

  • STARTTLS can be circumvented: attacker removes STARTTLS command (client sends unencrypted), or email server doesn't validate another server's TLS cert.
  • DANE (RFC 6698) binds X.509 certs to DNS names using DNSSEC; authenticates TLS without a CA.
  • Defines TLSA record — associates a TLS cert/public key with the domain; contains cert fingerprint; secure way to specify server's TLS capability without relying on STARTTLS.

SPF (Sender Policy Framework)

  • RFC 7208. Prevents spoofing of sender address.
  • Sender: list authorized email servers + policy → published as TXT DNS record.
  • Receiver: query SPF TXT record using MAIL FROM domain + sender IP → decide what to do.

DKIM (DomainKeys Identified Mail)

  • RFC 6376. Cryptographically signs email so a signing domain claims responsibility.
  • Signature attached to the email header; verifies sending domain (like SPF).
  • Recipients verify by querying signer's domain for the public key.
  • Strategy: message signed by private key of the administrative domain (not the originator's key like S/MIME/PGP); transparent to user (not in MUA); covers content + some headers.

DMARC

  • RFC 7489. Sender specifies policy on mail handling, reports, and frequency.
  • Works with SPF and/or DKIM; standardizes receiver authentication.
  • Authenticates the From domain (RFC 5322 header), not MAIL FROM/HELO (which SPF uses).
  • Requires From address align with an authenticated DKIM/SPF identifier.
  • Enables: domain owner gets reports; tells receiver what to do if SPF/DKIM fails.
